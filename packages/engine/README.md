# engine — граф сценария и расчёты

Разбирает сценарий, обрабатывает входы и считает наборы данных и показатели за отчётный
период; показывает превью любого узла.

- `analyze(scenario, registry, schemas)` — проверка без данных: плагины, параметры, ссылки,
  столбцы и их типы после каждого шага (шаги SQL и формулы проверяются в DuckDB на пустых
  таблицах нужных типов), порядок входов, наборов и формул, круговые ссылки. Все ошибки
  сразу, с узлом, в котором они найдены. `column_usage` — какие столбцы источника нужны
  сценарию (для `schema`). Столбец, который шаг записывает заново (формула с id столбца
  источника, `columns_written`), дальше — результат шага: столбец файла с этим id нужен,
  только если его читает сам шаг.
- `execute(plan, registry, history, period, workdir, options)` — расчёт. История приходит
  через `HistoryProvider` из контрактов: движок не знает о модуле `history` и о хранилище.
- `preview(plan, registry, history, period, workdir, target)` — превью узла: `sales`,
  `sales/dedupe` (вход после шага), `dataset:by_region`, `metric:revenue`.

## Как считается

1. **Вход** — действующая история, обрезанная по концу отчётного периода, и шаги по порядку.
   Начало чтения — самое раннее окно, которое нужно наборам и показателям (с учётом
   сравнений периодов и глубины `dedupe`); если какой-то шаг смотрит на всю историю, читается
   вся. Читаются только нужные дальше столбцы. Polars выполняет шаги лениво и потоково;
   на входах больше 2 млн строк сортировка, удаление дубликатов и объединение идут в DuckDB
   с лимитом памяти и выгрузкой на диск (`Limits`: бюджет — 60% доступной памяти, DuckDB
   получает половину; временные файлы — в папке данных).
2. **Объединение входов** — шаг `join` или `sql` ссылается на другой вход по `id`; входы
   считаются в нужном порядке, круговые ссылки — ошибка при проверке.
3. **Набор** — окно, условие, группировка (даты — по дням, неделям, месяцам, кварталам,
   годам), агрегаты, затем:
   - `compare: [previous_period, same_period_last_year]` — столбцы `revenue_prev`,
     `revenue_prev_change`, `revenue_prev_change_pct` (и `_ly`): те же группы за другой период;
   - `derive` — доля от итога (`share`, итог — по всему набору до топ-N), накопительный итог
     (`cumsum`), ранг (`rank`), формула из столбцов набора (`expr: fact / plan`);
   - `sort`, `top` и `others: Прочие` — строка со всем, что не вошло в топ;
   - `pivot: date` — значения столбца группировки становятся столбцами (`2026-01`, `2026-02`, …).

   Набор можно задать запросом SQL (`query`) к входам и другим наборам или кодом Python
   (`code` с функцией `build(tables, ctx)`); окно применяется к каждому входу до запроса.
4. **Показатель** — агрегат входа в своём окне, агрегат набора (`dataset` + `fn`), формула
   из других показателей, запрос SQL (`query`, одно число) или код (`value(tables, ctx)`).
   `compare` добавляет показатели `<id>_prev`, `<id>_prev_change`, `<id>_prev_change_pct`
   (и `_ly`); у формулы сравнение считается по сравнениям её частей.
5. Ошибка в узле помечает «не считался» только зависящие от него узлы; остальные считаются.
   Пропуски в загрузках за нужные окна — предупреждения. Ещё одно предупреждение (одно на
   загрузку, с узлом `input:…`) — если в файле загрузки, которую читает запуск, не было
   столбца источника, нужного сценарию (столбец переименовали в выгрузке, сверка его не
   нашла, и в этой загрузке он пустой). Читаются те загрузки, что попадают в окна узлов за
   их периоды; шагам нужно всё прочитанное, от нижней границы до конца отчётного периода.
   Проверка — по метаданным загрузок (`HistoryProvider.uploads`), без чтения данных; в превью
   её нет, как и других предупреждений о данных.

Формулы пишутся на SQL (диалект DuckDB) и переводятся в выражения Polars (`SqlTranslator`);
то, что не переводится (например, `levenshtein`), выполняет DuckDB. Деление на ноль даёт
пусто, а не ошибку.

**Код пользователя** (шаги, наборы и показатели на Python) выполняется в отдельном процессе
с лимитом времени и памяти (в Windows — Job Object), кроме ленивого режима шага. Ошибка
показывается с номером строки кода, `print` и `ctx.warn` попадают в журнал.

**Кэш узлов** (`NodeCache`, папка данных `cache/engine`): результаты входов, выборки для
превью, результаты запросов и кода. Ключ — хэш описания узла и шагов, версий приложения,
плагинов и библиотек, отпечатка истории, границ чтения и отчётного периода. Размер —
до 20 ГБ или 10% свободного места, давно не использованные записи удаляются. Предупреждения
и вывод кода сохраняются вместе с результатом и попадают в журнал и при чтении из кэша. Шаг,
который нельзя кэшировать (шаг «Python» с `cache: false`), выключает кэш для своего входа и для
всего, что от него зависит.

**Превью** показывает первые строки, число строк до и после каждого шага, набор или значение
показателя (вместе со сравнениями). Если в истории нужного входа больше 500 тыс. строк,
превью входа и шагов строится по выборке: строки с `hash(ключ) % K == 0`, примерно 200 тыс.
строк. Ключ — столбцы объединения (одна и та же функция для обеих сторон, пары сохраняются),
иначе столбцы `dedupe` (дубликаты сохраняются), иначе ключи источника, иначе номер строки.
Числа строк по выборке пересчитываются на всю историю и помечаются как приблизительные.
На истории 5 × 10 млн строк превью шага — около 0,3 с, первое превью (построение выборки) —
около 7 с, точные числа по всей истории — около минуты (`uv run python tools/bench_preview.py`,
4 ядра).

## Запуск отдельно

На готовой истории (например, от `python -m autogenerator.history --out`):

```
uv run python -m autogenerator.engine examples/sales/scenario.yaml --data история --period 2026-03 --out итоги
uv run python -m autogenerator.engine examples/sales/scenario.yaml --data история --period 2026-03 --preview dataset:by_region
```

Тесты модуля: `uv run agen test engine` (или `uv run pytest packages/engine`).
